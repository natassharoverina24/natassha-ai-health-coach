# Application Audit Findings

## Scope and method

This is a read-only Stage 0 audit. It does not change application behavior, business rules, Firebase rules, frozen specifications, or dependencies.

Evidence was gathered from the current application routes, components, repositories, deterministic planners, API routes, and tests. The public production login page was also checked at desktop and iPhone-sized viewports. Authenticated production screens could not be exercised because the browser session did not have a user account, so production-only interaction findings are explicitly marked for authenticated reproduction.

## Summary

- Total findings: **23**
- Blocker: **0**
- High: **8**
- Medium: **14**
- Low: **1**
- Recommended first fix: **make Office Lunch one clear, tray-aware flow from input through actionable coach guidance**

## Findings

| ID | Area / page / component | Finding | Severity | User impact | Suggested fix | Safe to fix now | Dependencies / risk |
| --- | --- | --- | --- | --- | --- | --- | --- |
| F-01 | Dashboard → Planner navigation → Office Lunch Optimizer | The user-reported “dead” Office Lunch Optimizer could not be reproduced without an authenticated production session. Static evidence shows the dashboard link targets `/planner#office-lunch-optimizer` and the planner button has a submit handler, but this only proves the controls exist—not that the production route, scroll target, loaded profile, and visible response work together. The test checks the `href` and component handler, not the authenticated end-to-end path. | high | The most important daily feature can appear clickable but give no visible useful effect, causing the user to abandon it. | In Stage 1, reproduce with an authenticated mobile session, add a dashboard-to-result interaction test, keep the section visible while loading, and show an explicit result or friendly partial state after every click. | yes | Must preserve Safari authentication and existing planner rules. Do not infer a production root cause before authenticated reproduction. |
| F-02 | `/planner` → `PlanningToolsPanel` → Office Lunch Optimizer | The optimizer collects only remaining calories and protein. It does not collect which tray items are actually available or selected, then renders recommendations for all 11 catalogue items. | high | Guidance can mention food that is not on today’s office tray, so the result is not actionable. | Feed the optimizer the user-entered available tray items and render actions only for that submitted menu, while preserving the deterministic budget and retained-insight rules. | yes | Requires a narrow input-contract decision or adapter; must not change thyroid, migraine, calorie, protein, or planner business rules. |
| F-03 | `/meal` → `OfficeLunchQuickForm` and `/planner` → Office Lunch Optimizer | Office lunch is split into two disconnected experiences. The meal form records selected items and editable macros, while the planner separately produces Eat/Reduce/Add/Skip guidance from budget only. Saving lunch does not produce an actionable checklist, and optimizer actions cannot be checked off. | high | The user must understand two pages and manually connect “what is available” with “what should I do.” | Make one mobile-first office-lunch flow: enter tray → run existing optimizer → show guidance/checklist → confirm the meal. | yes | Persistence for checklist completion may need an owner-owned existing pattern; do not duplicate meal logs or Decision Engine decisions. |
| F-04 | Mobile navigation → `BottomNav` / Settings | The mobile bottom bar sends “More” directly to `/settings`. Weight, Shopping, Supplements, and Reports are not present in the bottom bar and Settings contains no links to them. They remain reachable on desktop via Sidebar but are effectively undiscoverable on iPhone unless the URL is known. | high | Important existing features appear missing on mobile. | Turn “More” into a small route menu or add a clearly labelled tools list on Settings without redesigning the main navigation. | yes | Navigation change should be a separate scoped stage and regression-tested on Safari/iPhone. |
| F-05 | `/shopping`, Weekly Meal Prep, `PlanningToolsPanel` | Shopping is entirely manual (`addedFrom: "manual"`). Weekly Meal Prep is invoked with an empty ingredient catalogue, so it deliberately disables shopping-list and batch-cooking output even though the deterministic aggregation engine exists. | high | The user sees a weekly plan but receives no generated grocery list; the Shopping page does not deliver the expected coach assistance. | Provide an approved structured ingredient catalogue, generate the list from the weekly plan, and persist/check items through the existing owner-owned shopping repository. | no | Owner-approved ingredient quantities are still required. Inventing quantities or parsing template text is prohibited. |
| F-06 | Reports page and `reportsRepository` | The Reports page says weekly/monthly summaries are “generated automatically,” but the repository explicitly says generation logic is not implemented and no code creates report documents. | high | The empty state promises a feature that will never populate, which looks broken or unfinished. | Until deterministic generation is implemented, change the promise to an honest unavailable/coming-later state; later add an approved report generator as a separate feature. | yes for copy only | Implementing generation is new scope and requires approved rules; do not fabricate report data. |
| F-07 | Data-driven pages using `useFirestoreCollection` / `useFirestoreDoc` | Shopping, Supplements, Reports, Weight, Meal, Settings, and Progress commonly read only `data` and `loading`, ignoring the hook’s `error`. A permission, index, offline, or network failure therefore becomes an empty list or stale-looking screen instead of a retryable error. | high | Users can believe their records disappeared or that no data exists. Writes on several pages also have no friendly error state. | Add shared safe error/partial-state rendering and retry behavior, preserving last known data where available; never expose raw Firebase messages or index URLs. | yes | Must not disturb the robust partial-data behavior already used by `TodayCoachPlan`. |
| F-08 | AI Response Layer → `/api/ai/coach` and provider registry | Nutrition text estimation already follows local/cache → Gemini → Groq → OpenRouter Free → manual. However, the separate coach rewrite route defaults to Claude/Anthropic and has no free local/provider fallback; enabling it may require a paid service. | high | The product’s “100% free” promise is not guaranteed for the optional coach rewrite path, and an unset key makes the feature unavailable. | Keep deterministic structured coaching primary. Disable the paid-default rewrite in the free product or add an explicit free-only, no-spend provider configuration with local text fallback. | no | Provider quotas/models change. Any change must keep the Response Layer rewrite-only and must never add coaching decisions. |
| F-09 | `/meal` → Office lunch quick input | The tray selector supports the 11 fixed catalogue items but no safe custom item. It saves one joined meal record and nutrition totals, but does not display Eat/Reduce/Add/Skip advice or simple serving actions. | medium | A real office dish outside the catalogue cannot be represented cleanly, and logging can be mistaken for optimization. | Add an unresolved custom-item path using the existing confirmed nutrition flow, and keep guidance separate from nutrition estimation until confirmed. | no | Custom nutrition must use local/cache/free-provider/manual confirmation; never save unknown nutrition as zero. |
| F-10 | `/supplements` | Supplements are not fully passive: the page supports a daily taken/not-taken check. However, it ignores `timesOfDay`, forces `frequency: "daily"`, has no planned/skipped state, no reminder scheduling, and no “today” time context. | medium | The feature behaves like a basic checklist rather than useful, safe daily support. | Add user-confirmed schedules and planned/taken/skipped states, with reminders only for confirmed entries. | no | New persistence may require owner-only rules and tests. No dosage recommendations, medical claims, or inferred schedules. |
| F-11 | `/supplements` add form | The form accepts free-text dosage and silently substitutes `"1x"` when blank. That text is then displayed as if it were meaningful dosage information. | medium | A placeholder can look like health guidance or a confirmed instruction even though the app did not verify it. | Store an explicit “not provided” state instead of inventing `"1x"`; clearly label all supplement details as user-entered. | yes | Data migration/backward compatibility for existing `"1x"` records needs care. |
| F-12 | `/planner` → `PlannerWorkspace` | Planner loading still uses one `Promise.all` for Decision Engine context and planner context. Any one failure removes the full planner workspace, unlike the partial-data architecture used by Today. | medium | An optional-source problem can hide every planning tool and force a full retry. | Load from the established `TodayCoachPlan` read model or adopt typed per-source availability without changing planner logic. | yes | Avoid duplicating orchestration or altering completed Phase 1–8 modules. |
| F-13 | `/planner` → `PlannerWorkspace` error handling | The planner logs the raw caught error object with `console.error("PlannerWorkspace load failed:", error)`. The UI copy is safe, but the console may contain Firebase details or index URLs. | medium | Technical details can leak into production diagnostics and make support harder to sanitize consistently. | Log only a safe error code and source name in development, matching the existing safe-auth/emergency diagnostic pattern. | yes | Do not log user data, paths containing user IDs, tokens, or raw provider responses. |
| F-14 | `/planner` Emergency Planner vs Dashboard Emergency Mode | Two separate emergency experiences expose different disruption names and contracts. The planner tool includes missed breakfast, late dinner, restaurant, mall, travel, birthday, and wedding; the dashboard uses the newer user-declared Emergency Mode set. | medium | Users can receive two different interfaces for “plans changed” and may not know which one persists or affects Today. | Make Dashboard Emergency Mode the clear active-plan entry point and label the planner version as a non-persistent preview or retire its UI after confirming no route dependency. | no | Must not change existing Emergency Planner rules or `active_disruptions` security behavior during audit/fix staging. |
| F-15 | Dashboard → “Things I noticed” | Accept/Dismiss changes only component state. Refresh restores the original suggestion, while the labels sound like a durable preference choice. | medium | The user may think the coach learned a preference when nothing persisted. | Either label actions “Hide for now”/“Looks useful” with an explicit session-only note, or add minimal owner-owned persistence in a later approved scope. | yes for copy only | Persistence would require a separate data contract and rules review. It must not silently change Decision Engine rules. |
| F-16 | Meal, Weight, Shopping, Supplements | Destructive actions are executed immediately from small trash icons, with no confirmation, undo, or optimistic recovery. | medium | Accidental taps are likely on mobile and can remove meaningful logs without a recovery path. | Add an accessible confirm or short undo window, prioritizing meal and weight logs. | yes | Preserve repository semantics; do not add duplicate writes. |
| F-17 | Settings profile/goals | Inputs have labels but no `id` or `name`, so labels are not programmatically associated. Numeric parsing silently falls back to defaults or zero, and save failures have no friendly error. | medium | Accessibility suffers; Safari form behavior and password/form tooling may warn; invalid input can silently overwrite expected values. | Add stable `id`/`name`, field validation, disabled invalid submit, and friendly save errors. | yes | Must not change approved target formulas or defaults. |
| F-18 | Progress page | Six log sources are collapsed into one `coachDataLoading` flag and their errors are ignored. One slow source keeps the entire coach summary loading; one failed source can look like zero/empty data. | medium | Progress appears stuck or misleading even when most data is available. | Render per-section loading/empty/unavailable states and calculate only from explicitly available sources. | yes | Do not reinterpret missing data as zero or change Coach Score formulas. |
| F-19 | Dashboard copy | Core UI uses formal/technical English such as “No retained focus is available,” “Optional tools will appear,” “retained adaptive adjustment,” and evidence-window wording. | medium | The dashboard feels like an admin/debug interface rather than a supportive personal coach, especially for a non-technical Indonesian user. | In the dedicated polish stage, replace UI-only copy with concise, supportive Bahasa Indonesia while retaining source traceability and safety meaning. | yes | Copy must not add medical claims, certainty, or new recommendations. |
| F-20 | Dashboard and planner visual system | At least 29 teal/green accent references remain across Today, plans changed, adaptive insights, planner results, and progress. The hero itself gradients pink into teal. | medium | The visual hierarchy feels inconsistent with the intended soft-pink, feminine, calm product identity. | Replace decorative teal with muted rose, mauve, warm neutral, or slate; retain semantic success colors only where status meaning requires them. | yes | Recheck accessible contrast and dark mode; this belongs in its own visual-polish PR. |
| F-21 | Dashboard information hierarchy | Deterministic Office Lunch, Weekly Prep, Emergency, and Adaptive logic exists, but several outputs are either buried in a large planner page, shown only when optional inputs happen to be available, or represented as links rather than next actions. | medium | The user cannot easily tell what the coach wants them to do now, despite substantial logic already existing. | Surface only the relevant current action in Today, with a concise status and deep link to detail; do not recompute decisions in React. | no | Requires UX prioritization and must continue reading `TodayCoachPlan` only. |
| F-22 | `/planner` mobile usability | All completed tools are stacked into one long page. Forms and result lists are responsive, but there is no tool-level collapse, active-result focus, or return-to-top/navigation affordance. | medium | On iPhone, reaching Office Lunch from a dashboard anchor can still leave the user in a dense multi-tool screen with weak confirmation of what changed. | Use focused sections/accordion or a dedicated Office Lunch entry flow in Stage 1 while keeping existing routes valid. | yes | Avoid a broad navigation redesign in the Office Lunch bug-fix PR. |
| F-23 | Test and production audit coverage | Component tests verify links, handlers, and deterministic outputs, but there is no authenticated browser smoke path covering dashboard → planner anchor → Office Lunch result on production mobile. The public login page itself rendered correctly at an iPhone-sized viewport during this audit. | low | Integration regressions can pass unit tests and appear only after deployment. | Add a credential-free emulator-backed smoke test where possible and maintain a short authenticated manual Safari checklist for production. | yes | Do not commit credentials or create production accounts automatically. |

## Recommended staged order

1. **Stage 1:** reproduce and unify the Office Lunch tray-input → optimizer → actionable checklist flow.
2. **Stage 2:** make Supplements safely schedule-aware and user-confirmed.
3. **Stage 3:** connect Weekly Meal Prep to Shopping only after approved ingredient quantities exist.
4. **Stage 4:** polish Bahasa Indonesia, information hierarchy, and pink visual consistency.
5. **Stage 5:** formalize the free-only AI strategy, especially the optional Anthropic Response Layer path.

No Stage 1 code or behavior is included in this audit.
